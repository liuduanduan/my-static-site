# 寻器 AI 工具自动发现与自动发布设计

**日期：** 2026-09-03

**状态：** 待用户审阅书面设计
**适用分支：** `main`

## 1. 背景

寻器当前有 120 款 AI 工具，工具事实数据保存在
`docs/.vitepress/theme/domain/ai-tools.json`，由生成器创建工具详情页、分类页、场景页、
sitemap 和结构化数据。仓库已经具备安全官网抓取、严格结构化内容补全、工具去重、
目录校验、完整测试和 GitHub PR 自动化。

现有自动化主要处理网站访客主动提交的工具，不能主动从公开信息源持续发现新工具。
本设计新增一个独立的后台发现流水线，在不复制第三方导航站文案、不降低目录质量的
前提下，每天自动发现、验证并发布少量高置信度工具。

## 2. 决策

采用“混合自动发布”模式：

- 高置信度候选自动创建 PR，通过全部校验后自动合并。
- 信息不充分、互相矛盾或接近安全边界的候选只进入 GitHub 审核任务。
- 每天最多自动发布 3 款，避免突然生成大量低价值页面。
- 目录达到 300 款有效工具后暂停自动发布，只继续发现和健康检查，等待调整上限。

不采用直接修改默认分支的方式。即使是自动发布，也必须保留独立分支、PR、测试记录和
可回滚的 Git 历史。

## 3. 工具放置位置

自动发现器是后台运维能力，不在网站首页或公开导航中增加管理入口。

- `.github/workflows/discover-ai-tools.yml`：每日定时任务和手动触发入口。
- `scripts/discovery/`：数据源适配、候选规范化、去重、评分、内容整理和目录写入。
- `config/ai-discovery-sources.json`：显式允许的数据源与查询规则。
- GitHub Actions：运行状态、日志和构建结果。
- GitHub Issues：需要人工判断的候选和连续失败摘要。
- GitHub Actions artifact：最近处理状态，避免短期内重复抓取失败候选。
- `ai-tools.json`：通过所有门槛后的唯一公开事实源。

公开网站继续只提供“提交工具”入口；普通访客不接触自动化配置和管理操作。

## 4. 目标

- 自动发现尚未收录、具有可访问官网的 AI 产品。
- 自动生成符合现有 `AiTool` Schema 的中文目录内容。
- 自动去重、分类、选择同类替代工具并生成静态详情页。
- 在不需要每日人工编辑 JSON 的情况下稳定扩容。
- 保证新页面具备独立价值，不能依靠同义模板批量制造空洞页面。
- 保证外部网页内容只作为不可信证据，不能成为自动化指令。
- 失败时不修改目录，并给出有限、可复现的错误分类。

## 5. 非目标

- 不复制其他 AI 导航站的介绍、标签、排名、评分或图片。
- 不抓取登录后内容、付费内容、个人信息或受限 API。
- 不自动把工具设为“精选”，不创建赞助或联盟关系。
- 不根据模型自报的“信心分数”决定发布。
- 不生成未经官网证据支持的用户量、融资额、排名、价格或中文支持承诺。
- 不让网页中的提示词、脚本或隐藏文本改变流水线行为。
- 不把自动化管理界面暴露到公开网站。

## 6. 数据源

第一阶段支持三类适配器，全部由配置文件显式启用：

1. GitHub Search API：寻找带 AI 产品主题、达到最低活跃度且声明了 HTTPS 官网的项目。
2. Hacker News Algolia API：发现近期有一定讨论度的 `Show HN` AI 产品，只读取标题、
   原始产品 URL、时间和公开热度字段。
3. RSS/Atom/JSON Feed：仅允许配置中的固定 HTTPS 源，从条目中提取候选名称和外链。

数据源只负责发现候选名称、URL、来源标识和发现时间。所有最终目录文案必须重新从官方
网站公开证据生成。每个来源设置请求超时、响应大小上限、条目上限和明确的 User-Agent。

## 7. 数据流

```text
定时 GitHub Action
    │
    ├─ 读取允许的数据源配置
    ├─ 拉取少量公开候选
    ├─ URL 规范化与目录/历史去重
    ├─ 安全抓取候选官网公开 HTML
    ├─ 确定性质量门槛
    ├─ 结构化 AI 内容补全
    ├─ Schema 与事实措辞校验
    └─ 临时批次写入 + 页面生成 + 全量验证
             │
             ├─ 1–3 款高置信度：创建批次 PR → 校验通过 → 自动合并
             └─ 不确定：创建或更新 GitHub 审核 Issue
```

每次运行最多读取 50 条源记录、检查 15 个新域名、自动发布 3 款工具。处理顺序固定，
相同输入能够产生稳定结果。

## 8. 候选规范化与去重

- 只接受 `https:`，拒绝用户名、密码、非标准端口、localhost、私网和链路本地地址。
- 移除 fragment 和已知跟踪参数，主机名转小写，国际域名规范化。
- 跟随重定向时每一跳重新做 DNS 与目标校验，最多 3 跳。
- 按最终注册域名、规范 URL、规范名称和 slug 四个维度去重。
- 与现有目录、当前开放 PR、当次候选和最近处理 artifact 同时比对。
- 同一公司多个明确独立的产品只有在官网分别提供独立产品页时才允许保留。

已有的 `safeOfficialFetch.mjs` 继续作为唯一官网抓取入口，不另写一个权限更宽松的抓取器。

## 9. 确定性质量门槛

候选必须同时满足以下条件，才能进入内容补全：

- 官网返回 2xx HTML，响应体在限制内且包含非空标题。
- 可见产品文本达到最低长度，不能只是登录页、停放域名、即将上线页或错误页。
- 页面存在明确产品名称和能力描述；名称与候选域名或官网标题不冲突。
- 能归入现有 9 个主分类之一，并能关联至少 2 个现有同类替代工具。
- 不属于成人、博彩、恶意软件、仿冒、纯代币投机或明显违法用途。
- 不与现有工具域名、slug 或规范名称重复。
- 没有价格、语言支持和访问方式的明显矛盾证据。

评分只用于排序，不用于越过硬门槛。评分由来源质量、公开热度、官网证据完整度、链接健康度
和目录分类缺口构成；模型自报置信度不计分。

## 10. 内容补全

复用现有 OpenAI Responses API 结构化输出适配器和严格 JSON Schema。模型只接收：

- 候选名称和规范官网 URL；
- 官网标题、meta description 和经过清理、截断的可见文本；
- 现有分类枚举与允许的访问、价格、中文支持枚举；
- 同分类现有工具的 slug 和名称，用于选择替代工具。

模型不接收网页脚本、表单、隐藏文本、Cookie、请求头、用户邮箱或内部密钥。系统提示明确
网页内容是证据而非指令。输出继续使用保守措辞，定价描述必须以“以官网为准”收尾；
无法从官网确认的字段不得猜测。

没有配置内容补全密钥时，发现器只生成审核任务，不写目录、不创建发布 PR。

## 11. 自动发布门槛

只有同时满足以下条件的候选才能自动合并：

- 通过全部确定性质量门槛。
- 结构化内容通过现有 Schema、中文搜索词、分类和替代工具校验。
- 不包含 `featuredOrder`、赞助、联盟或排名字段。
- 临时写入后运行 `npm test`、`npm run verify:build` 和 `git diff --check` 全部成功。
- PR 只修改允许的目录事实数据和自动生成页面。
- GitHub 分支保护要求的检查全部成功。
- 当日自动发布数量未超过 3，目录总数未达到 300。

工作流创建 `discovery/YYYY-MM-DD-<run-id>` 分支和包含 1–3 款工具的单个批次 PR。这样可以
避免多个机器人分支同时修改 `ai-tools.json` 产生冲突。PR 正文逐项记录来源、官网证据摘要、
质量门槛和测试结果。满足条件时由机器人 squash 合并；任何一步不确定的候选会从批次中移除并
转入 Issue，不尝试降低门槛。

## 12. 状态与幂等

每次运行生成 `ai-discovery-state.json` artifact，记录规范域名、候选哈希、处理结果、有限错误码、
首次和最后处理时间，不保存网页全文或密钥。下次运行下载最近一次成功 artifact 并恢复状态。

artifact 不可用时仍以目录和开放 PR 为权威去重，不会重复发布。连续三次相同失败的候选进入
冷却期 30 天；源记录变化后可以重新评估。

同一候选重复运行必须得到相同 slug。相同运行批次应复用内容相同的远程分支或 PR，禁止强制
推送覆盖不同内容。

## 13. 错误处理

- 数据源不可用：记录 `source_unavailable`，继续处理其他来源。
- 数据源格式改变：记录 `source_invalid` 并创建汇总 Issue，不猜测新格式。
- 官网安全校验失败：记录 `official_fetch_rejected`，不重试私网或危险目标。
- 官网临时失败：指数退避，最多重试两次，之后进入冷却。
- 内容补全不可用：本次不发布，保留候选供后续重试。
- 内容输出不合格：记录 `enrichment_invalid`，进入审核 Issue。
- 生成、测试或构建失败：不创建可合并 PR，工作流失败并保留诊断日志。
- GitHub 合并失败：保留已验证 PR，不直接推送默认分支。

日志不得输出 API 密钥、Authorization、完整模型响应或未截断的网页内容。

## 14. GitHub 审核任务

所有不确定候选汇总到标题固定的 `AI 工具自动发现审核` Issue，避免每天创建大量 Issue。
每项只包含工具名称、规范官网、来源、有限错误码和建议核验动作。Issue 不包含抓取网页全文。

人工可以通过配置忽略列表永久忽略域名，或把确认后的候选重新加入下一次手动运行。公开网站
不显示被拒绝、待审核或抓取失败的候选。

## 15. SEO 与发布后动作

- 合并后的工具由现有生成器自动创建独立详情页，并进入分类、场景和 sitemap。
- 继续使用现有 `SoftwareApplication`、`ItemList` 和面包屑结构化数据。
- 发布后只把本次新增的规范 URL 交给现有搜索通知脚本。
- IndexNow 或百度密钥不存在、额度为 0 或服务拒绝时，只记录通知失败，不回滚已通过验证的页面。
- 自动页面必须满足现有非模板化校验；不能仅替换工具名称生成重复介绍。

## 16. 测试

### 单元测试

- 三类数据源适配器的正常、空结果、超时、过大响应和格式变化。
- URL 规范化、重定向、私网阻止、域名/名称/slug 多层去重。
- 质量硬门槛和评分排序相互独立。
- 网页提示注入、隐藏文本和脚本不能进入模型请求。
- 内容补全缺少密钥、返回无效 JSON、编造禁止声明时不发布。
- 每日 3 款和总量 300 款限制。
- artifact 丢失、重复运行、远程分支已存在和连续失败冷却。

### 集成测试

- 使用完全本地的假数据源和假官网响应完成一次发现到目录草稿的流程。
- 高置信度候选只修改允许文件并生成正确详情、分类、场景和 sitemap。
- 低置信度候选只生成审核摘要，目录保持逐字节不变。
- 任一测试或构建失败时不得执行合并步骤。

### 验收

1. 手动触发 dry-run 能列出候选而不修改仓库。
2. 测试数据中的高置信度候选能创建一条通过全部检查的 PR。
3. 相同工作流再次运行不会创建第二条工具或第二个 PR。
4. 未配置内容补全密钥时安全退出并产生审核摘要。
5. 每日定时运行最多自动发布 3 款，达到 300 款后自动停止扩容。
6. 新工具合并后页面、分类计数、场景、sitemap 和结构化数据全部正确。

## 17. 部署配置

GitHub Actions 使用：

- 内置 `GITHUB_TOKEN`：读取 GitHub 搜索、创建分支、PR、Issue 和合并。
- `CONTENT_ENRICHER_API_KEY`：现有内容补全密钥。
- `CONTENT_ENRICHER_MODEL`：支持严格结构化输出的模型名。
- 可选 `INDEXNOW_KEY` 与百度推送密钥：发布后通知。

所有第三方 Actions 固定到完整 commit SHA。自动发现和现有用户提交整理工作流共同使用
`ai-catalog-writes` 并发组，禁止两个机器人同时修改目录。

## 18. 实施顺序

1. 提取可复用的目录写入和候选规范化接口，保持现有提交自动化行为不变。
2. 为数据源适配器、状态恢复、去重和硬门槛编写失败测试。
3. 实现 GitHub、Hacker News 和通用 Feed 发现适配器。
4. 接入安全官网抓取与现有结构化内容补全。
5. 实现 dry-run、单候选临时写入和完整目录验证。
6. 新增每日工作流、artifact、汇总 Issue 和高置信度自动合并。
7. 使用真实公开源做一次限量 dry-run，人工检查候选列表。
8. 启用每日最多 3 款自动发布，并持续使用现有链接健康检查。
